### 2. override가 재빌드를 견디는지 실측 확인 방법

`data/_gold/user_pl_cells.json`에 3건 신설(`was`=정정 전 값, `note`=raw 경로·캐시 경로·
account_id·검산 전문). **직접 실행해서 확인**: override 추가 후 `build_root_masters.build_pl()`
을 실제로 재실행했고, 로그에 `pl overrides: 199 set`(기존 196건 + 신규 3건, MISSING 0건)이
찍혔다 — 즉 override가 정상적으로 이 3개 행을 찾아 upsert했다. 이후 combo-diff로 결과가 정확히
기대한 6셀만 바뀌었음을 재확인(위 표).

**주의사항(다음 세션을 위해 기록) — `pl_breakdown_master.json` 자체는 이 override로 보호되지
않는다.** `build_pl_breakdown.py`의 `_GOLD_CELL_OVERRIDE`는 항목 1-24만 커버하고 25-31(OCI 확장,
50th pass 신설)엔 override 훅이 아예 없다(코드 실측 확인 — `for n in OCI_ITEMS: val = v.get(n)`
루프가 `_GOLD_CELL_OVERRIDE`를 참조하지 않음). 그래서 그 빌더를 통짜 재실행하면(`main()`) 이
3셀은 **여전히 버그인 FS-API 캐시**에서 다시 잘못된 부호로 채워진다. root `PL_breakdown.json`은
안전하다 — `build_root_masters.build_pl()`이 매번 `user_pl_cells.json`을 마지막 단계에서
UPSERT하기 때문(방금 실측한 그대로). 이 이유로 **`RUN_PL_GOLDEN=1 pytest tests/
test_pl_breakdown_golden.py`(빌더 재실행)는 이번 세션에서 의도적으로 미실행** — 돌리면 이
3셀이 즉시 원상복구되고 방금 갱신한 골든과 불일치가 난다. 대신 패치된 파일에 대고 매니페스트만
