## 미결 (orchestrator 작성)

신설한 OCI 항목에서 **소계(항목25)와 구성요소(26~30)의 합이 안 맞는 셀이 대량으로 나온다.**
`4cca165` 산출물 실측이다.

```
비교 가능 273셀 중  잔차 >1%  = 103건 (38%)
                   잔차 >10% =  33건
```

부호가 뒤집히는 사례도 있다. 최악은 푸본현대생명 2024.3Q — 총액 △1,488억인데 세부 합은 +3,947억이다.

### 파서 잘못이 아닐 가능성이 높다 (확인한 것)

푸본현대 2024.3Q 원천(`data/dart/_fs_api_cache/00459844_2024_11014_OFS.json`)을 직접 열어서
확인했다. 항목27로 들어간 `보험계약자산(부채)순금융손익`(+2,652억 누계)은 이름만 평범할 뿐
`account_id` 가 `ifrs-full_OtherComprehensiveIncomeNe...` 라 **실제로 OCI 섹션 항목이 맞다.**
매핑은 옳았다.

문제는 원천 자체다. 그 파일에서 `당기손익으로 재분류되는 세후기타포괄손익의 구성요소` 누계는
△1,490억인데, 같은 파일이 태깅한 그 하위 구성요소들(신용손실 △16 · CF헤지 +53 ·
FVOCI금융자산 +1,237 · 보험계약순금융손익 +2,652 · 재보험 +5)의 합은 +3,931억이다.
**DART XBRL 추출본 안에서 소계와 구성요소가 이미 안 맞는다.**

### 확인해 줄 것

1. **API 추출본이 본문 XML 표보다 불완전한 것인지 확인해라.** DART 재무제표 API 는 표에 있는
   행을 다 태깅해 주지 않는 경우가 있다. 본문 XML 의 포괄손익계산서 표에 API 추출본에 없는
   OCI 구성요소(예: 확정급여제도 재측정요소, 해외사업환산, 관계기업 지분 등)가 더 있는지
   푸본현대 2024.3Q 와 잔차 상위 몇 건으로 대조해라.
2. 더 있다면 그것들을 항목으로 추가할지, 아니면 현재 5개 세부만 유지할지 판단해서 근거와 함께 보고해라.
3. 없다면 **원천이 스스로 안 맞는 것**이므로 그대로 둔다. 이 경우 그 사실을 도메인 문서에 남겨라.

### 하지 말 것 (중요)

**파생값으로 갈아끼우지 마라.** 소계를 구성요소 합으로 바꾸거나, 구성요소 하나를 잔차로 채워
억지로 닫지 마라. 이 저장소 원칙이다 — 발행사 총괄표와 세부표가 어긋날 때 파생값으로 대체하면
한 셀이 여러 룰의 입력이라 RED 이 늘고 헤드라인까지 뒤집힌다. 공시된 대로 둔다.

화면은 이미 이 전제로 처리돼 있다. designer 가 잔차를 `기타 포괄손익(미분류)` 막대로 명시해서
브리지를 닫는다(`eec64e0`). 즉 **지금 화면은 안 깨진다.** 이 티켓은 원인 규명이 목적이다.
