## 미결 (sender 작성) — 적용후 mmult 전수 감사: **닫히지 않는다.** 게이트가 안 보던 축이 있다

owner 지시로 mmult 를 3개 축 × {적용전, 적용후} 전수 재계산했다. 상관행렬은 룰엔진에서
그대로 import 했다(재타이핑 금지): `R7`(7×7) · `MARKET_M`(5×5) · `R4`(4×4).

**내가 어제 "적용후 mmult 불일치 0"이라고 한 것은 틀렸다.** 게이트가 찍는 그 0 은
**게이트 자신의 좁은 검사범위 안에서만** 참이었고, 나는 그걸 전체로 일반화했다.

### 1. 전수 결과

| 축 | 컬럼 | 계산가능 | FAIL(tol 2.0) | FAIL(5%) | 계산불가(하위결측) |
|---|---|---|---|---|---|
| A 생명장기 `17 = f(29-35)` | 적용전 | 350 | 5 | 1 | 136 |
| A 생명장기 `17 = f(29-35)` | **적용후** | 345 | **10** | 4 | 141 |
| B 시장 `19 = f(36-40)` | 적용전 | 340 | 3 | 0 | 146 |
| B 시장 `19 = f(36-40)` | **적용후** | 296 | **4** | 1 | 190 |
| C 기본요구자본 `15 = f(17-20) + 21` | 적용전 | 484 | **0** | 0 | 2 |
| C 기본요구자본 `15 = f(17-20) + 21` | **적용후** | 480 | **36** | 9 | 6 |

### 2. 게이트가 왜 0 이라고 했나 — 검사범위 구멍 두 개

`_transition_mmult_after()` 를 읽었다:

```python
for (c, q), m in sorted(byq.items()):
    if c not in _TRANSITION_APPLIERS:      # (1) 선택 경과조치 18사만
        continue
...
_TRANS_PARENT_SUBS = {17: (...R7), 19: (...MARKET_M)}   # (2) item15 가 없다
```

- **(1) 비-applier 회사는 적용후 mmult 를 아예 안 본다.** A축 FAIL 4건 중 3건이 여기 숨어 있었다
  (신한이지 · 하나손해 · KB라이프 — 셋 다 applier 아님).
- **(2) 축 C(기본요구자본)는 적용후 검사가 통째로 없다.** owner 가 이번에 짚은 그 축이고,
  FAIL 36건 전부가 여기 있다.

즉 게이트의 "0" 은 **거짓말이 아니라 범위 밖**이다. 그러나 결과적으로 false-green 이었다.

### 3. 축 C — 전제가 틀린 게 아니라 데이터가 틀렸다

처음엔 "적용후엔 이 항등식이 원래 성립 안 하는 것 아닌가"를 의심했는데, **아니다**:

```
적용전  484/484 PASS (tol=2.0)     <- 완벽
적용후  444/480 PASS (tol=2.0)     <- 대부분 닫힌다. 36건만 안 닫힌다
```

**적용후에도 444건이 tol 2.0 으로 닫히므로 항등식은 적용후에도 성립한다.** 그러니 36건은
의미론 불일치가 아니라 **셀 결함**이다. 부호도 섞여 있어(±) 단일 공식오류도 아니다:

회사별로 연속 분기가 묶여 나오는 것도 구조적 원인을 시사한다.

### 4. 축 A — 산술적으로 불가능한 셀 2건 (가장 확실한 결함)

**신한이지손해보험 2025.1Q** — `item35(대재해)후 = 43` 인데 부모 `item17후 = 10` 이다.

```
item   적용전   적용후
29        0        0
30        0        0
31        5        5
32        1        1
33        4        4
34        3        3
35        2       43     <- 여기만 튄다
17       10       10     <- 부모는 그대로
적용전: 공시 10.00 계산  9.90  PASS
적용후: 공시 10.00 계산 47.01  FAIL (78.7%)
```

**분산 후 부모가 개별 하위위험보다 작을 수는 없다.** 43 짜리 하위를 담은 부모가 10 일 수 없다.
`item35후` 나 `item17후` 중 하나가 틀렸고, 적용전이 깨끗하니 **적용후 셀이 오염**이다.

**하나손해보험 2025.2Q** — `item34(사업비)후 = 44.43` 인데 이건 **`item35(대재해)` 의 값**이다.

```

적용후: 공시 1,820.00 계산 1,555.96  FAIL (17.0%)
```

한 칸 밀림(cell shift) 지문이다. 부모후는 전과 같은 복사본이라 안 움직였다.

**KB라이프생명 2024.2Q** — 부모후는 16,176 그대로인데 하위후 30/31/33/34 가 전과 다르다
(33: 10,787 → 12,364). 계산 17,357 vs 공시 16,176 (6.8%).

### 5. 축 B — 1건, 이미 documented

흥국화재 2024.4Q (37.8%). `_AFTER_SUBRISK_NOT_DISCLOSED` 등재분(image-only PDF, owner
GOLD-SCAN 대기)이라 게이트가 정당하게 제외한 건이다. **참고로만 적는다.**

미래에셋 2023.2Q A축 FAIL 도 기존 documented RED(8_life, scan-only)와 같은 건이다.

### 6. 또 하나의 사각 — 계산 자체가 불가능한 버킷이 많다

`계산불가` 열이 A 136~141 · B 146~190 이다. 전체 486 버킷의 **28~39%** 가 하위 결측이라
mmult 를 시도조차 못 한다. 이건 FAIL 로도 안 잡히고 조용히 넘어간다
(`[[feedback-coverage-census-mandatory]]` 의 SKIP-on-missing 문제와 같은 부류).
B축 적용후가 190 으로 가장 심하다.

### 7. 요청

1. **축 A 2건(신한이지 2025.1Q item35후 · 하나손해 2025.2Q item34후)은 지문이 명확하니
   원문 재확인 후 정정**해 달라. KB라이프 2024.2Q 도 같이 봐 달라.
2. **축 C 36건**은 원인 진단이 필요하다. 회사별 연속 분기로 묶이니 표 구조 문제일 가능성이
   있다. 적용후 세부(17/19후)를 어느 표에서 뽑는지부터 확인해 달라.
3. 축 B 적용후 하위결측 190건은 별건이지만, 채울 수 있는 게 있으면 알려 달라.
